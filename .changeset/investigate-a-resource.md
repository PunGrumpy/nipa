`nipa investigate web-1`, or `nipa why web-1`, finds the server, load balancer, database, volume or Kubernetes cluster with that name or ID and says what's wrong with it, so you no longer have to know which of `server inspect`, `server history`, `server logs`, `lb inspect`, `db inspect`, `volume ls`, `k8s ls` and `quota ls` holds the clue. It lists problems first, then warnings, then the checks that passed, and each problem shows the field and value it read, such as `status: ERROR`, and the commands to run next, such as `nipa server history web-1`. A server is checked for its status, a task that hasn't finished an hour after its last action, a lock, its last failed action with who asked and when, console log lines that show a kernel panic, the out-of-memory killer, a cloud-init failure or a full disk, volumes that aren't in use, a missing address, and the compute quotas when a create failed. A load balancer gets the verdict `nipa lb inspect` ends with, a database the problems `nipa db inspect` names, a volume its error states and attachments to servers that are gone, and a cluster its nodes and masters that aren't active. A quota at 90% or more is a warning when the resource is being made or failed. A read that fails is a warning, not an error. When every check passes, nipa says no problem was found in what it can see, and it always names what it can't see, such as the hypervisor's logs, which only Nipa Cloud's operators can read. When a name fits more than one kind, nipa lists a command for each, and `--kind server`, `lb`, `db`, `volume` or `k8s` picks one. `--json` prints `{ profile, project, investigation }` with each finding's `severity`, `check`, `summary`, `evidence` and `next`, in the shape of an error's `next` and with your `-P` and `-p`. It exits with code 0 whatever it finds, so a script reads the problems with `jq '.investigation.findings[] | select(.severity == "problem")'`. In a pipe, it prints the resource's ID.
