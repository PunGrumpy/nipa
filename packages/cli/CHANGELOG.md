# nipa-cli

## 0.1.9

### Patch Changes

- 7c60f86: `nipa investigate web-1`, or `nipa why web-1`, finds the server, load balancer, database, volume or Kubernetes cluster with that name or ID and says what's wrong with it, so you no longer have to know which of `server inspect`, `server history`, `server logs`, `lb inspect`, `db inspect`, `volume ls`, `k8s ls` and `quota ls` holds the clue. It lists problems first, then warnings, then the checks that passed, and each problem shows the field and value it read, such as `status: ERROR`, and the commands to run next, such as `nipa server history web-1`. A server is checked for its status, a task that hasn't finished an hour after its last action, a lock, its last failed action with who asked and when, console log lines that show a kernel panic, the out-of-memory killer, a cloud-init failure or a full disk, volumes that aren't in use, a missing address, and the compute quotas when a create failed. A load balancer gets the verdict `nipa lb inspect` ends with, a database the problems `nipa db inspect` names, a volume its error states and attachments to servers that are gone, and a cluster its nodes and masters that aren't active. A quota at 90% or more is a warning when the resource is being made or failed. A read that fails is a warning, not an error. When every check passes, nipa says no problem was found in what it can see, and it always names what it can't see, such as the hypervisor's logs, which only Nipa Cloud's operators can read. When a name fits more than one kind, nipa lists a command for each, and `--kind server`, `lb`, `db`, `volume` or `k8s` picks one. `--json` prints `{ profile, project, investigation }` with each finding's `severity`, `check`, `summary`, `evidence` and `next`, in the shape of an error's `next` and with your `-P` and `-p`. It exits with code 0 whatever it finds, so a script reads the problems with `jq '.investigation.findings[] | select(.severity == "problem")'`. In a pipe, it prints the resource's ID.
- c25940b: `nipa mcp` offers an `investigate` tool, so an AI assistant that you asked "Why is web-1 broken?" can ask nipa instead of piecing the answer together from several lists. It takes a `name` (a name or ID) and optionally a `kind` (`server`, `lb`, `db`, `volume` or `k8s`) and a `project`, runs the checks that `nipa investigate` runs, and returns the same `{ profile, project, investigation }` that `nipa investigate --json` prints: findings with problems first, each with the evidence it read and the commands to run next. When a name fits more than one kind, the tool returns the `ambiguous_name` error with each choice, and the assistant asks again with `kind`. The tool only reads, like the other 17.
- b028eaf: Start `nipa` faster from npm by caching the compiled code between runs in Node.js's compile cache, which `NODE_DISABLE_COMPILE_CACHE` turns off.
- 3b3a4a9: `nipa mcp` lets an AI assistant that you already use, such as Claude Code, Claude Desktop, Cursor or Codex, read your Nipa Cloud project with the session nipa saved, so it can help you find out why something is down. nipa holds no AI key and calls no model: the command runs a Model Context Protocol server on stdin and stdout, and you add it to the assistant, for example with `claude mcp add nipa -- nipa mcp`. It offers 17 tools that only read: they list and inspect servers, volumes, networks, security groups, load balancers (with a diagnosis of which part is down), databases, Kubernetes clusters, quotas and flavors, read the end of a server's console log and its history, and search servers in every project. Each returns the JSON that the matching command prints with `--json`. Nothing starts, stops, creates or deletes anything. `-P` and `-p` before `mcp` pick the profile and project for the whole run, and each tool takes a `project` of its own for one call, without saving it. nipa never prompts here: when the session expired, a tool returns an error that asks you to run `nipa login` in a terminal, and the next call works once you did. A failed tool returns the same message, reason and next commands as `--json`. Messages go to stderr, so stdout carries only protocol messages. Other commands don't start slower for it, apart from a few milliseconds for a larger package.

## 0.1.8

### Patch Changes

- 17d9f2a: When two servers share a name, `nipa server stop worker` and the other commands that take a server now list each candidate on its own line with its full ID, its status and its address, so you can tell which one you meant and copy its ID. Before, the error ran the IDs together on one line that wrapped in the middle of an ID. The error shows at most five, then says how many more there are and to run the `ls` command with `--json` for their IDs. Volumes, networks, load balancers and databases that share a name get the same list with the columns their `ls` shows, such as a volume's size, and security groups list their IDs. With `--json`, the error stays one line with its `ambiguous_name` reason, `hint` holds the same list as a person sees, and a new `data.ids` holds every ID, so a script no longer reads them from `hint`.
- 2ef6d55: nipa now refuses to follow redirects from Keystone and the Space API, so a gateway that redirects can no longer send your token or password to another host, and a profile URL that redirects fails with an error naming the target. Requests give up after 30 seconds instead of hanging, a response that stalls or isn't JSON ends in a clear error instead of a stack trace, and resource names and API messages can no longer move the cursor, change the window title or reorder text in your terminal.
- c94cb2a: `nipa server ls` now fits your terminal and works with `grep`. In a narrow terminal it drops the Flavor column, then Age, then shortens `(Kubernetes worker)` to `(worker)`, then prints each server as two lines, so rows no longer pile on each other and a name or address is never cut. In a pipe it now prints a header and one tab-separated line per server (ID, name, status, address, flavor and creation time as an ISO date), so `nipa server ls | grep web` filters the servers and stops printing the table on stderr. This changes what a pipe receives: it used to be one ID per line. To get the IDs, run `nipa server ls | tail -n +2 | cut -f1`, or `nipa server ls --json | jq -r '.servers[].id'`. Update any script that feeds this to `xargs`: it would read every field as a server name, and a script that picks a line by number now gets the next server. Pick the ID first, and match the name's own field before anything that stops a server, because `grep` searches every field and a short word can match an ID: `nipa server ls | awk -F'\t' '$2 ~ /^web/ {print $1}' | xargs -n1 nipa server stop --yes`.
- a166898: A failed command with `--json` now writes exactly one line of JSON to stderr and nothing to stdout, so a script can tell "log in" from "retry later" without matching English. The document has a `status` (`action_required` when a person has to act first, such as logging in or fixing the command line, otherwise `error`), a stable `reason` such as `login_required`, `token_expired`, `not_found`, `ambiguous_name`, `network_error`, `unknown_option` or `unknown_command`, the `message`, and a `hint` and `next` commands when there are any, for example `nipa login` for an expired session. A bug in nipa under `--json` writes an `internal_error` document in place of a stack trace. A successful `--json` command no longer writes notes, such as the session expiry warning, or the `Using profile` line to stderr, and `nipa whoami --json` logged out now prints its `{ "loggedIn": false }` document and exits 1 without an error message after it. Without `--json`, errors look the same as before.
- 7250c86: `nipa -p Beta server ls` now looks at another project for one run, without `nipa switch` changing the project every terminal uses. `-p, --project` takes a project name or ID, works before or after the command (and before `os`, `tf` and `exec`), beats a folder's link, and is never saved. nipa prints `Using project Beta`. A 32-character ID costs no extra request, and a project whose name looks like an ID still works. A name or ID that no project has exits with code 1 and lists your projects, and a name that two projects share fails and lists their IDs, in `login`, `switch` and `link` too, instead of picking the first. A revoked session under `-p` still says to run `nipa login`.

  The commands nipa suggests in a hint, a note or a `--json` error, such as `nipa -p Beta server start db-1`, now keep your `-P` and `-p`, so copying them acts on the project you were looking at. `nipa -p Beta open` names Beta in the portal and fails for a project you don't have. `nipa login -p` still chooses the project to save. The commands that never read a project (`completion`, `whoami`, `doctor`, `switch`, `link`, `unlink`, `logout` and `profile`) refuse `-p` with exit code 2 instead of ignoring it, so `nipa -p Beta switch Alpha` can't save a project by accident. Tab completion offers your project names after `-p` and finds the command after it, in bash, zsh, fish and PowerShell. `nipa exec -p Beta env` now says that nipa's options go before `exec`.

- 808d709: `nipa server search web` finds servers across every project you can use, so you no longer open them one by one. It matches a piece of a server's name, ID or any address, ignoring case, and treats the query as plain text. Without a query it lists every server. nipa asks each project live, four at a time, and saves nothing, so a server that the portal, Terraform or Kubernetes just made shows up. In a terminal, the matches sit under their project, the project `nipa server ls` shows is marked `(current)`, and a name that a project gives to two servers has each server's ID under it, and two projects with the same name each show their ID after it. When only one server matches, nipa prints the command to inspect it, such as `nipa -p Beta server inspect worker`, and the commands it suggests keep your `-P`. A folder's link doesn't narrow the search, and `nipa -p Beta server search web` searches only Beta. In a pipe, it prints a header and one tab-separated line per match (ID, name, project, project ID, status, address, flavor and creation time), so `nipa server search web | cut -f1,3` and `grep -i active` work. `--json` prints the matches with their `project`, how many `projects` it `searched` out of the `total`, and the projects that `failed`, each with its `message`, a `reason` code and the HTTP `status`. When a project can't be read, because you aren't allowed to list its servers or it takes more than 15 seconds, nipa still prints the servers it found, says `in 4 of 6 projects` instead of claiming all of them, lists the projects it skipped and exits with code 1. With `--json` it prints its document and exits with code 1 without an error document. When your session expired, it prints that one error and tells you to log in.
- f861d04: `nipa profile ls --json | head -1` no longer ends with a stack trace when the reader closes the pipe. nipa now decides colors for stdout and stderr separately, so `nipa profile ls 2>log` on a terminal stops writing color codes into the file, `CI=1 nipa --help | cat` is plain, and `FORCE_COLOR` and `NO_COLOR` behave as documented: `FORCE_COLOR=1` tints messages on a pipe but leaves piped help plain. Prompts follow the same decision, so `--no-color` also turns off the colors of a prompt. nipa no longer prompts or draws a spinner under `--json` or when `CI` has a value, which keeps a script from stopping at a login prompt and keeps spinner frames out of captured output, and the new `--non-interactive` option turns both off anywhere. The update notice is two lines instead of a box, shows only where nipa can prompt, and `NO_UPDATE_NOTIFIER` turns it off.

## 0.1.7

### Patch Changes

- 7e26b01: nipa writes `config.json`, `auth.json` and its cache files by renaming a finished temp file into place, so a crash or a second nipa command can't leave a half-written file, and it keeps `~/.config/nipa` and `~/.cache/nipa` private (`0700`, files `0600`) on every write, not only when it creates them. When the update check can't reach GitHub, nipa remembers that for a day instead of waiting on it after every command, and a cache it can't write no longer fails the command.
- e2eb3e6: Tab completion in bash no longer expands `$(…)` or `$VAR` inside a project, server, volume, image, network, security group, load balancer or database name that comes from Keystone or the Space API, and it escapes names with spaces or quotes so they insert as one word. zsh keeps a `:` in a name. Run `nipa completion --install` again, or restart your shell if it loads the script with `eval`, to pick up the new script.
- 8fbd78a: `-h` inside a cluster of short options, as in `nipa server stop web -yh`, prints the command's help instead of running the command. `nipa profile list` is the same as `nipa profile ls`, like every other `ls` subcommand.
- ffd7ffe: `nipa os`, `nipa tf` and `nipa exec` run on a profile that has no Space API URL, such as one added with `nipa profile add` for another Keystone without `--space-url`. They failed with "has no Space API URL" since 0.1.5, although only `server ls` and the other resource commands need that URL. A program that can't start, such as a script whose `#!` interpreter is missing, exits with code 126 and a message instead of a stack trace.
- 22b8cb7: A `config.json` that nipa can't read, such as one with a typo or a profile with a bad URL, now fails with an error that names the file, instead of loading as a nipa 0.1 file with only the `prod` profile and deleting the other profiles on the next save. A profile on production's Keystone keeps its Space API URL however the Keystone URL was typed, with or without `/v3`.

## 0.1.6

### Patch Changes

- 22d34a3: Add `nipa db inspect`, which takes a database cluster's name or ID and answers whether it's healthy and how to reach it. It shows the engine and version, status, health and when Trove last checked it, flavor with its vCPUs and RAM, storage, zone, address with the engine's default port, allowed CIDRs, replicas, whether the general and slow query logs are on, and the 5 newest backups. Its last line says the database is healthy and where to connect, or what needs attention, such as a primary that isn't active or a latest backup that failed. `--json` prints all of it under `database`, with every backup, the engine's `defaultPort` and a `problems` list of what's wrong and where. `nipa db ls --json` gives each primary `id`, `zone`, `vcpus`, `ramMb`, `allowedCidrs` and `healthCheckedAt` too, and every status list colors completed backups green and failed ones red.
- 22d34a3: `nipa db ls` shows a database's internal address when it has no external IP. The Address column was blank for these, and `--json` gave `externalAddress` as `""` instead of `null`.
- f31bf3b: Add `nipa doctor`, which checks your setup in one go and says what to fix: the config files, which profile the run uses and why, whether its Keystone and Space API answer and how fast, the session and when it expires, whether Keystone and the Space API accept its token, the folder's link, `openstack` and `terraform`, and a newer nipa from the last update check. It changes nothing and never asks for a password, so it works in scripts. `--json` prints each check's `id`, `status`, `summary` and `hint`. It exits with code 1 when a check fails, and a warning doesn't change the exit code.
- 49bc449: Add `nipa flavor ls`, which lists the flavors a server can have, smallest first, with their vCPUs, RAM and type. The Space portal calls them machine types, so `nipa machine-types` does the same, and so does `nipa flavors`. The ones only database clusters use don't show. In a pipe, it prints one flavor name per line.
- 49bc449: Add `nipa k8s ls`, which lists the Kubernetes clusters in your project with their Kubernetes version, nodes, active node count and age. `nipa os coe` can't find Magnum on Nipa Cloud production, so nipa finds each cluster through the servers Magnum made for it. `nipa kubernetes` and `nipa coe` do the same. `nipa server ls --json` gives each Kubernetes node its `version` too.
- 61c0eed: Add `nipa lb inspect`, which takes a load balancer's name or ID and shows why it doesn't serve. It prints the load balancer's status, health, virtual IP, external IP and flavor, then each listener, backend group and member with its status and health, and marks in red each part that isn't `ACTIVE` and `ONLINE`. The last line names what stops it, such as `2 of 3 members are down`, or says that every part is healthy. `--json` prints the whole load balancer with its listeners, backend groups and members. Tab completes load balancer names after `nipa lb inspect`.
- 49bc449: Add `nipa network ls`, which lists the networks your project can use with their status, type, zone and age. A VPC network is one of your project's private networks, and an external network is a shared pool of external IPs. `nipa networks` does the same.
- 3c4252d: Add `nipa link [project]`, like the Vercel CLI's `vercel link`, which saves the profile and a project in `.nipa/project.json`. Commands in that folder and the folders below it use them, so a Terraform folder for staging needs no `-P staging`, and `nipa switch` in other folders doesn't change it. nipa exchanges the token for the linked project before each command and doesn't save it. `nipa unlink` removes the link, and `nipa whoami --json` gives `link`.
- 51f4c90: Add `nipa open`, which opens the profile's Space portal in your browser, like `vercel open`. `nipa open server`, `volume`, `network`, `sg`, `lb` or `db` opens that list, and a name or ID after it opens that resource's page. In a pipe, or with `--url`, nipa prints only the URL and doesn't open a browser. The portal opens the project you last used in it, because a URL can't pick one.
- 92bda92: Tab completion after `nipa os` completes server names after `server show`, `stop`, `start`, `delete` and the other commands that take only servers, and the names after `--flavor`, `--image` and `--network`. nipa reads them from the Space API, keeps them for a minute, and never asks for a password on a Tab press.
- 0cb45a4: Add `nipa quota ls`, which shows each quota of your project, such as servers, vCPUs, RAM and volumes, by group, with how much it uses, its limit and the percent used. A quota at 80% or more shows in yellow and one at its limit in red, and a note counts them, so you can see why a create failed or how much room is left. `--json` prints each quota's group, name, used, limit and unit, and a pipe gets one tab-separated line per quota with its unit. `nipa quota`, `nipa quotas` and `nipa limits` do the same.
- fe436ef: Add `nipa login --remember`, which saves your password in the macOS Keychain, or with `secret-tool` on Linux, so later logins ask only for an OTP code. Keystone has no refresh token, so a session still lasts 24 hours. When Keystone refuses a saved password, nipa deletes it and asks. `nipa logout` and `nipa profile rm` delete the saved password. Commands that use a session with less than 30 minutes left print a note with the login command first.
- 9df4221: Add `nipa server history` and `nipa server logs` to find out why a server failed. `history`, or `events`, lists the actions on a server, newest first, with who asked, the result and the request ID. `logs` prints the server's console log, cloud-init output included, and `--tail 20` keeps the last 20 lines. A server that never booted has no console log, so nipa says so and names `nipa server history`. `nipa server inspect` now shows Nova's task while the server is busy, whether it's locked, and its last action, such as `create failed 26m ago by Ann`, and names `history` and `logs` for a server in Error. `--json` prints all of it, and `inspect --json` adds `taskState`, `locked` and `lastAction` to the server.
- 9afaa9b: Add `nipa server inspect`, `start`, `stop` and `restart`, which take a server's name or ID. `inspect` shows the server's flavor with its vCPUs and RAM, zone, addresses, volumes and security groups, and `--json` prints them. `start`, `stop` and `restart` call the Space API, like the Space portal's buttons, then wait until the server finishes. `stop` and `restart` ask first, and `--yes` skips the question. `--no-wait` returns once the Space API takes the action, and `--timeout 10m` waits longer than the default 5 minutes. Tab completes server names after these commands. `nipa server ls --json` gives each server `vcpus`, `ramMb`, `zone`, `volumes` and `securityGroups` too.
- 340528d: `nipa sg inspect <Tab>` completes security group names.
- 340528d: Add `nipa sg inspect`, which takes a security group's name or ID and shows its description, the servers that use it with their addresses, and its inbound and outbound rules. Each rule shows its protocol, ports, and the CIDR or security group it allows by name. A note says when an inbound rule opens SSH, RDP or a database port to the internet. `--json` prints the group in the shape `nipa sg ls --json` uses, and adds each rule's `remoteGroupName` and the group's `servers`.
- 49bc449: Add `nipa sg ls`, which lists the security groups in your project with their inbound and outbound rule counts, age and description. `--json` prints each rule's direction, protocol, ports and remote. `nipa security-group` and `nipa security-groups` do the same.
- 49bc449: Add `nipa volume ls`, which lists the block storage volumes in your project with their status, size, type, the server each one is attached to, and age. `nipa volumes` does the same. Volume statuses such as `in-use` and `creating` get the same colors as server statuses, and read as "In use" and "Creating".

## 0.1.5

### Patch Changes

- 197c333: Add `nipa completion --install`, which saves the tab completion script where bash, zsh or fish loads it, so the shell doesn't run nipa each time it starts. nipa rewrites the saved script when its version changes, so new commands complete after an update. `nipa completion` without a shell uses the one in `$SHELL`.
- 47797cd: `nipa server ls` marks the servers that a Kubernetes cluster made, such as `k8s-control-plane-1 (Kubernetes master)`, from the Magnum tags the portal reads too. `--json` gives each server `kubernetes`, which is `null` for a server you made, or the cluster's `clusterId` and the node's `role`. The troubleshooting page explains why `nipa os coe` and other commands can't find their service on production.
- 587c9ac: Give production's Space API only to profiles on production's Keystone. In 0.1.4, a staging profile got production's Space API, which refused its token, so `nipa server ls` said the session had expired. nipa now drops that URL from such profiles. `nipa profile add --space-url` takes the Space portal URL, such as `https://portal-stg-epc.nipa.cloud`, saves its `/api`, and checks that it answers. With another Keystone and a terminal, `profile add` asks for the portal URL. Without one, `server ls`, `db ls`, `lb ls` and `ip ls` say the profile has no Space API URL before they ask for a login. A profile that 0.1.4 saved with a portal URL gets its `/api` when nipa loads it, and a Space API URL that answers with a web page gets an error that says so.
